# Learning release: a brief guided start

## Status

Proposed on 2026-09-15. The [comprehensive first-run brief](../../feature-briefs/kwilt-first-run-onboarding.md)
owns the complete journey, copy, data boundaries, implementation slices, and verification gates.
This document defines the smallest useful learning release; nothing here asserts shipment.

## Question

Can a new person recognize a relevant Kwilt offer, see trustworthy personal value, and take one
useful action without feeling trapped in setup?

## Audience and demand

- Primary audience: `audience-aspirational-family-organizers`.
- Representative persona: Maya.
- Hero: `jtbd-move-the-few-things-that-matter`.
- Flow: `job-flow-maya-review-budget-reality-before-spending`.
- Improve entry, minimum setup/resume, intentional choice, and trust/repetition.
- Keep non-Money arrivals in the study: an apparently excellent Money conversion screen still
  fails if it hides the person's actual reason for downloading Kwilt.

## Release shape

Start with a connected interactive prototype of the full Money path and one complete alternative,
including preview and a meaningful failure state. Then build an internal deterministic vertical
slice: starter → correct authentication/access → one real connection → a scoped finding → owned
budget review/save → usable Money. Add bounded AI and optional budget-linked app controls after
the underlying useful path works.

The prototype may use explicitly labeled example data. Production entry must never use those
fixtures. Do not promote the shared entry until all four visible capability offers have real
destinations and usable first-value paths.

## Included

- Real Kwilt mark, existing heavy fonts, light canvas and original atmospheric visual family.
- Clear primary offer and visible goals/to-dos, chores, and meals alternatives.
- One meaningful choice before existing sign-in; returning/exact-entry precedence.
- Existing Pro access policy and a focused one-time offer, with actual product verification later.
- One-institution start, optional contextual composer, truthful asynchronous handling.
- One to three earned findings, inspectable evidence, and a proposal handed to its owning editor.
- Budget saved on Money; optional user-selected app pauses and contextual alerts.
- Scoped preview, resumption, and named nondestructive Dev Tools rehearsal presets.

## Explicitly excluded

- New financial health scores, credit reports, investment profiles, cash accounts, or securities advice.
- A new free-year promotion or unlimited-service promise.
- Mandatory household-wide financial intake, forced identity work, or universal Agent interview.
- Installed-app discovery or app selection inferred from merchant transactions.
- Automatic budget/rule changes on an AI suggestion or generic “Continue.”
- New broad anonymous-account infrastructure, copied competitor assets, or fabricated social proof.

## Review gates

1. **Visual/interaction:** seven-frame connected path, default and large text, keyboard-visible
   composer, real controls, legible terms, stable dock, and obvious alternatives/escape.
2. **Source/state:** production-safe route adapters, no demo injection, account-scoped receipts,
   permission/access separation, no duplicate writes, correct return precedence.
3. **Internal runtime:** complete deterministic loop, empty/sparse/loading data, model fallback,
   purchase cancellation/restore, optional app-control denial, all alternate first values.
4. **Native/service:** relevant signed-device banking, rule enforcement and reversal, commercial
   availability, notification behavior, and biometric policy if offered.
5. **Learning:** moderated new-user evidence, revisions, and follow-up on a meaningful repeat use.

## Quality posture

Logic, state, AI prompt construction/validation, and scheduling use the project's TDD posture.
Presentation iterates in the native runtime with focused accessibility/branching tests. Keep
Simulator, signed-device, backend, Store, and release-candidate evidence separate. Do not use a
passing screenshot review as a proxy for the job being delivered.

## Approval boundary

The request authorizes this plan and its documentation. It does not authorize implementation,
new purchases/prices, backend resets, publishing, or a new worktree. The next artifact is the
connected mockup specified by the brief, when Andrew proceeds with design iteration.
