# Evaluate Learning: Contextual Recipe Chat

## Learning questions
- Do people understand the dock icon as Chat about the visible meal?
- Which of the four offers is naturally chosen, and which is ignored or confused?
- Does filling rather than auto-sending create useful control or unnecessary friction?
- Do answers materially use the exact recipe evidence?
- Does “Make it ours” create an expectation that a revision was already saved?

## Evidence plan
- Observe the full Recipe Home → drawer → card → submitted timeline turn → response → close loop on the iPhone 17 Pro Simulator.
- Test at least one recipe with long ingredients and one Kwilt catalog recipe.
- Inspect Chat evidence disclosure and answer text for the exact recipe version.
- Record any moment where the person restates information already present or looks for a save receipt that does not exist.

Supporting evidence: the intended card is selected quickly, its request is immediately legible in the timeline, follow-up steering handles additional constraints, answers cite recipe-specific facts, and closing returns exactly to Recipe Home.

Disconfirming evidence: the Chat control competes with Meal Plan, the grid feels like marketing, cards trigger the wrong job, answers stay generic, or revision language implies a saved change.

## Instrumentation
Use local observation and existing Chat turn/evidence records for this learning release. Do not add ingredient-level behavioral tracking.

## Decision rule
Proceed to a permanent Recipe proposal/apply slice only after repeated use shows people want to retain a variation and clearly understand the difference between a conversational draft and a saved Recipe version. Otherwise simplify card copy, order, or count.

## Expected next action
Visually QA the drawer, dogfood each starter, then decide whether recipe revision persistence or better contextual reads is the next bottleneck.
