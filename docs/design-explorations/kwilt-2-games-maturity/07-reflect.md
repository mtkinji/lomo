# Reflect: Oddball table-play feedback

## The bet

Oddball would stay legible and lively if the host corrected a preselected scoring group, the reveal used one short static cue, the rules lived only on the teaching screen, and play continued until an unmarked player reached eight.

## Did the bet hold?

No. One observed table session surfaced five connected failures:

- scoring felt broken;
- result entry began with everyone selected, forcing subtraction instead of direct selection;
- the reveal did not provide a real visible or spoken three-second countdown;
- the table wanted background music and a rules reference during play;
- the eight-point ending made the game feel indefinite.

The underlying majority/sole-unique incentive remains the working rule, but its host entry and pacing did not support a trustworthy, finishable table experience.

## Updates applied

- Keep `jtbd-help-us-enjoy-being-together` at validated; this is negative implementation evidence, not evidence against the job.
- Revise Oddball to six questions, direct selection from an empty state, a visible and spoken countdown, bounded background music, and an in-game rules affordance.
- Derive the public marker only from an explicitly identified sole unique player and allow a fixed final result to have shared winners.

## Taxonomy gaps surfaced

None. The feedback sharpens the existing “complete a fair, responsive shared game” step in `job-flow-maya-start-playing-together`.

## What I'd do differently

Treat host result entry as part of the core game mechanic, not administrative cleanup. A table-play pass should explicitly time the reveal-to-result transition and the full game length before calling the loop mature.

## Next questions

After the revision, can a 3–4-player group and a 6–8-player group finish six questions without a scoring dispute, and does the table ask to play again?
